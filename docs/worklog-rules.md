## 規則本文

# 每日工作日誌

在任何專案完成一個階段後，主動把該事項寫進當天的工作日誌。不用問使用者要不要寫，直接寫。

## 路徑與檔名

- 目錄：`~/Documents/Obsidian Vault/每日工作日誌/`
- 檔名：民國年月日 7 碼，例如 2026-08-17 → `1150817.md`（民國年 = 西元年 − 1911）
- 檔案不存在就建立；已存在就讀進來，在對應專案區塊底下 append

## 何時寫

每完成一個「階段」就寫，不要累積到收工才補：

- commit 完成
- MR 開好或合併
- bug 確認修好
- 有結論的討論／會議
- 設計、規格、架構討論（含 spectra discuss / propose、方案取捨）
- 環境設定、部署、資料庫維護這類沒有 commit 的事

## 專案怎麼分類

**在哪個專案做的事，就記在那個專案底下。** 專案名取工作目錄的名字（`project_a`、`project_b`、
`worklog-app`…），不是你覺得它「屬於哪一類」。

- 一次對話橫跨多個專案 → 分別記到各自的區塊，不要全部塞進同一個
- 一個專案第一次出現 → 新增一個 `## <專案名>` 區塊
- `其他` **只**留給不屬於任何專案目錄的事：環境設定、對帳、跨專案的規則或工具調整。
  不要拿 `其他` 當萬用桶
- 分不出來時用「我剛才動的檔案在哪個 repo」判斷，不要猜

**寫進去之前一定要先定位區塊。** 不要用 `>>` 之類的方式直接 append 到檔尾——
檔尾很可能是別的專案的區塊，那樣會把事情記到別人家。正確作法是讀進檔案、
找到對應的 `## <專案名>`、插在那個區塊的最後一筆後面；找不到才在檔尾新增區塊。

## 格式

```markdown
## project_a
- [feat: 歷史瀏覽記錄畫面](http://gitlab.example.com/group/project_a/-/merge_requests/123)
- 修正 room 版面 scroll 問題

## project_b
- 畫面調整：sidebar 收合動畫
```

- 專案名用 H2，事項用一層 bullet
- **每行開頭用行內程式碼標一個狀態**，接著才是內容（見下方狀態表）
- **一件事一行，不要展開細節。**有 MR / issue 就寫成 `[標題](連結)`，寫完就結束——不要在底下補子項說明改了什麼、做了哪些決策，那些細節本來就寫在 MR / issue 裡面了
- 沒有 MR / issue 連結的事（提案、環境設定、討論結論）才寫一句白話，同樣**只有一行**
- 同專案已有區塊就往下加，不要重開第二個同名區塊
- **同一支 change 的每一行都要帶同一個 slug 前綴**，寫成 `slug：描述`。
  提案、開分支、開 MR、封存都算，MR 那行也一樣要寫成
  `` `待合併` [my-feature：feat: 標題](MR 連結) ``。
  少寫 slug 的那一行會被當成另一件事，同一支 change 就會在看板上裂成好幾張卡

## 狀態

Spectra change 的生命週期：待辦 → 提案中 → 暫存 或 實作中 → 待合併 → 已歸檔

| 標籤 | 意思 |
| --- | --- |
| `待辦` | 只有議題，還沒開始寫提案 |
| `提案中` | 正在寫提案與規格，文件還沒齊 |
| `暫存` | 提案與規格都完成、已 park，還沒開工 |
| `實作中` | 已開分支動工 |
| `待合併` | 已開 MR，等審查與合併 |
| `已歸檔` | MR 已合併、spec 已歸檔 |
| `完成` | 不走 change 生命週期的一次性工作（環境設定、對帳、規則調整、版本升級） |

- 標的是「這件事**在當天推進到哪個狀態**」，不是它現在的狀態——日誌是當天的紀錄，寫下去就不再改
- 同一支 change 會在不同天各出現一次（提案一天、開 MR 一天、歸檔一天），這是正常的，不要為了避免重複而省略

## 注意

- 寫之前先讀當天檔案，避免重複記同一件事
- 事項用中文白話，不要貼 commit hash 或整串 diff
- 這是私人筆記，不進 git
